**History:**

The original Sun-1 P2 Bus intent was to provide memory expansion for
Sun-1 Boards from 256K onboard memory by 256K expansion memory at low cost.
At this time, the bus consisted of the CPU RAM signals
driving the expansion RAMs directly without any additional buffers.

Soon after starting Sun, it became clear that a main memory size of 1 MByte
was a minimum requirement. To accomodate this, signals were added to the
P2-Bus to allow it to address up to 2 MBytes of expansion memory.
The most common system configuration at that time was a 1 MByte system
with 256K on the CPU board and a partially populated 768K expansion board.
A substantial number of systems was built like that.

Over time, demand for memory increased on the side of our customers
resulting in a need to build 2 Megabyte systems.
At this point two problems became clear: First, the memory board
did not work properly in the 1 MByte configuration required for the second megabyte,
and second, the P2-Bus exhibited problems when connecting three boards.

The first problem was solved by redesigning the memory board.
The second problem was solved by using FAST logic on the memory board
for receiving the P2 control signals. FAST has a logic threshold of
1.5 Volt which greatly enhances the noise immunity over the previously
used Schottky parts.

Next we ran out of power and cooling in the Model 100U when
installing the Xylogics disk controller power hog.
This problem was solved by redesigning the memory board (again),
decoding the RAM chips 2-way saving approximately 2.5 Amps per board.
This change required two signal changes on the P2-Bus and the addition
of a new signal indicating memory refresh cycles, P2.REFRESH, to the Bus.

The new memory board, called the Sun-2 or low-power memory board,
was implemented such that Sun-2 memory boards remained compatible
with Sun-1 CPU Boards. However, Sun-2 CPU boards were incompatible with
Sun-1 memory boards, thus obsoleting the installed base of memory boards
in the field.

Next we added the Sun-2 video board to the P2-Bus.
This required two additional signals not present on the original
P2-Bus, namely an asynchronous handshake signal P2.WAIT and an early
read/write line P2.R/W\.

Designing in the Sun-2 memory board and the Sun-2 Video Board required a
total of three additional signals which were taken from the six ground
wires present in the original Sun-1 P2-Bus, leaving us with three ground returns.

Next we found that the P2-Bus still did not work for the planned 120/170 configuration,
consisting of CPU, 4 Megabyte Memory, and Video Board, due to excessive
noise on the bus. This problem was solved in two steps:
First, we added 100-OHM parallel terminators to the video board,
and second, we went to a four-layer backplane for the P2-Bus.
The first step resulted in a configuration requirement that a video board
or equivalent terminator board be present on all 120/170 systems
and that the video board be installed at the opposite end of the CPU
along the P2-Bus.

With these changes, the current P2-Bus does support the 120/170 configurations.
However, the noise level on the bus is still high, and the noise level
is unacceptably high in systems that do not have the proper termination.
Thus the issue at hand is that the current P2-Bus is not working properly
in all possible system configurations. A redesign to the P2-Bus means
redesigning the CPU, Memory, and Video Board.

In retrospect, it seems that it would have been better to abandon
the Sun-1 P2-Bus when designing the Sun-2 P2-Bus.
The primary reasons this did not happen back then was a need to
allow a phased upgrade in the field from 1.5 to 2.0 Boards.
Also, the full limitations and implications of the P2-Bus were
not known at the time the design was finalized.

**P2-Bus Problem-Matrix:**

*1. FAST Drivers for Addresses and Data.*
Due to the number of buffers
between CPU and Memory the current P2-Bus Boards require FAST drivers
on virtually all P2-Bus signals. The problem with this is that
the FAST risetimes cause excessive coupling, reflections, and ground shifts
on the P2-Bus.
Solution is to reduce number of buffers between CPU and memory, thereby
reducing the need for FAST parts and driving with ALS parts or MOS Parts instead.

*2. Multiplexed Addresses.*
The current P2-Bus uses multiplexed addresses
which causes three problems: 1) Imprecise control of RAS Hold and CAS setup
times on the memory chips, 2) P2-Bus Noise generated during RAS/CAS multiplexing,
and 3) Incompatibility with 256K RAMs.
Solution is to demultiplex the address.

*3. Unidirectional Data Signals.*
The problem with this is the high number
of ICs required to drive the bus and the number of signals taken up.
Solution is to go to a bidirectional data bus.

*4. Missing Read Strobe.*
The current Multibus P2-Bus has no read strobe.
This increases P2-Bus noise because read data is always enabled
but fluctuates during memory board accesses.
Solution is to add a read strobe which is necessary anyway for a
bidirectional data bus.

*5. Insufficient Capability for Video Board Interface.*
The current P2-Bus does not provide worst-case timing for asynchronous
devices such as the video board.
Solution is to provide a separate address space for asynchronous devices.
At the same time, this increases available memory space on the P2-Bus to
8 Megabytes.

*6. Total Length of P2-Bus Signals.*
A number of P2-Bus signals have excessive length causing reflection problems.
This is due to the PCB layout of the current board set.
Solution is better placement of P2-Bus interface chips.

*7. Insufficient Number of Ground Wires.*
The number of ground wires on the
current P2-Bus is too small and they are not placed close enough to the critical
P2-Bus control signals.
Solution: Increase number of grounds and place them between control signals.

**Risk Assessment:**

The judgement below is my best assessment of the situation, ranking
the risk by machine/package in order of increasing risk.
Keep in mind that the P2-Bus problem is primarily a function of the
configuration and the backplane the Sun-2 Boards are used in.

Risk appears lowest for the Model 120 and 170 because these packages
have the video board termination and 4-layer backplanes.
At this point, I have no failure data suggesting that a P2-Bus noise
problem was ever observed on these systems, and we have tested these
systems extensively.
However, data is limited due to the small numbers of 120s and 170s built so far.

Risk is medium for the Model 100 and 150 because these packages
have no P2 termination and use the old 2-layer backplanes.
Even though these systems are limited to three boards on the P2-Bus
(CPU plus 2 Megabytes) the measured P2-Bus noise on a 2 Megabyte Model 100
is higher than on a fully loaded 4 Megabyte 120 system.
These measurements are supported by failure data indicating that
2 Megabyte 100Us systems that work at 5.0 Volt VCC start failing
with memory errors at 5.5 Volt VCC (P2-Bus noise gets worse with
increasing voltage).
Unfortunately, there appears to be no practical way to add a
terminator to the P2-Bus of the installed base of 100/150s.

Risk is even high for customers that want to use our boards as
board-level products in their own cardcages due to the fact
that those cardcages most likely have inadequate backplane construction
and that the customer might not have a video board/terminator present.

Risk is highest for customers that plan to repackage our boards while
extending the length of the P2-bus, e.g. Schlumberger/Analyst.
There is a fair chance that this will not work at all.

**Proposed Solution:**

1) Complete design cycle of Model 50 design.

2) Redesign Multibus CPU, Memory, and Video Board based on Model 50 design.

3) Convert existing 120/170 to 120A/170A based on new board set.


**Benefits of Proposed Solution:**

1) Working and Manufacturable Design.

2) Memory boards are compatible with 256K RAMs.

3) Maxmimum memory size is 8 Megabytes.

4) Opportunity exists to add the Ethernet interface to the CPU Board.

5) RasterOp chip and DVMA work correctly with all of memory.
